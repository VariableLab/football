## 🔴 阻断上线的 7 个关键问题

### 1. 生产预测仍用旧模型，准确率不足

```
当前生产：线性 4 权重融合 → 48.6% 准确率
新 LR 43维：回测 56.6%，但尚未部署到 PredictionEngine
```

**影响**：上线即展示一个比随机（33%）好不了太多的预测，用户信任度会立即丧失。

### 2. 策略/投注 API 无后端鉴权

```
64 个 API 端点中，仅 12 个有 Depends(get_current_active_user)
策略相关 API（/api/strategy/*）全部公开
```

**影响**：任何人可以未认证调用策略优化、参数修改等敏感接口，属于安全漏洞。

### 3. 无数据库迁移机制

- 没有 Alembic / 任何 migration 工具
- Schema 变更靠 `init_db()` 直接 create_all
- 54MB 的 SQLite 数据库无迁移保障

**影响**：上线后任何模型/表结构改动都可能导致数据丢失或服务中断。

### 4. SQLite 不适合生产环境

- SQLite WAL 模式虽支持并发读，但写入仍是单锁
- 54MB 数据库，41 个定时任务同时写入 → 高概率锁竞争
- 无备份策略（无 cron、无 S3 同步）

**影响**：生产负载下可能出现 `database is locked` 错误，且数据无冗余保障。

### 5. 测试覆盖率极低

```
7 个测试文件，主要是 smoke test
39,785 行 Python 代码 → 测试代码约 1,000 行 → 覆盖率 < 3%
```

**影响**：核心预测引擎（2,143 行）、主 API（1,922 行）几乎无测试保护，上线后 bug 无法快速定位。

### 6. 无 Docker 化 / CI/CD

- 无 Dockerfile、无 docker-compose
- 无 GitHub Actions / 任何 CI pipeline
- deploy.sh 是手动 shell 脚本，非幂等

**影响**：部署流程不可重复、不可回滚，无法自动化测试验证。

### 7. 无可观测性基础设施

- 没有 Prometheus metrics 端点
- 没有 Grafana 仪表盘
- health_daemon 存在但告警冷却机制刚修复，未验证
- 48 处 error handling 但无结构化错误追踪（无 Sentry）

**影响**：上线后无法实时监控系统状态，问题只能事后翻日志。

## 🗺️ 达到上线水平的建议路线图

### Phase 0：安全加固（1-2 天）

1. 策略 API 加 `Depends(get_current_active_user)`
2. 修复 deploy.sh Nginx 重复 server block
3. SECRET_KEY / ADMIN_API_KEY 强制从环境变量读取 ✅（已做）

### Phase 1：核心模型部署（3-5 天）

1. LR 全量训练完成 → 部署到 PredictionEngine
2. Residual NN 集成到预测管线
3. 竞彩结果自动同步脚本
4. 验证：生产准确率 ≥ 53%

### Phase 2：基础设施（5-7 天）

1. SQLite → PostgreSQL（或至少加 WAL 优化 + 自动备份）
2. 添加 Alembic 数据库迁移
3. Dockerfile + docker-compose
4. GitHub Actions CI（lint + test）

### Phase 3：测试与监控（3-5 天）

1. 核心预测引擎单元测试（目标覆盖率 ≥ 50%）
2. API 集成测试
3. 添加 `/metrics` Prometheus 端点
4. Sentry 错误追踪

### Phase 4：前端优化（2-3 天）

1. 前端构建管线（压缩、hash 指纹、CDN）
2. 配置正式 SSL 证书（Let's Encrypt）
3. 静态资源缓存策略

---

## 🎯 一句话总结

> **项目在数据规模和架构设计上做得不错，但在安全、测试、部署、监控这四个生产必备维度上严重不足。** 建议按上述 Phase 0→1→2→3→4 顺序修复，预计 **2-3 周** 可以达到基本上线水平。不建议现在上线——48.6% 的准确率 + 无鉴权的策略 API + SQLite 单锁 + 零测试 = 上线即翻车。
